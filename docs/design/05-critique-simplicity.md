# 르방이 설계 단순화 리뷰 — 과설계 판정 10건

기준: 1인 개발·원샷 구현·백엔드 0·v1 범위. 확정 결정(풀 루프·실시간 다마고치·네이티브·순수 코어)은 건드리지 않았다 — 아래는 전부 구현 방식·중복·연출 범위에 대한 것이다.

---

## 1. 시뮬레이션 코어가 문서 사이에 **두 벌**이다 — 적분기 쪽을 폐기하라

**무엇이 과한가**: 시뮬 문서는 닫힌 함수 모델이다 — 타임스탬프+느린 누적값만 저장하고 활성도·부피·단계는 전부 `(now − lastFedAt) × 온도배율`의 파생값, catch-up O(1). 반면 아키텍처 문서는 완전히 다른 코어를 정의한다: `fullness`·`activity`·`rise`·`sourness`를 0..1 float로 **저장**하는 60초 고정 스텝 적분기 + `remainderMs` + 가산성 프로퍼티 테스트 + "2주 방치 = 스텝 2만 회". 상충은 코어에 그치지 않는다 — catch-up 상한 60일 vs 90일, `location: room/window/fridge` vs `temperature: cold/room/warm`, 시계 역행 처리(전 타임스탬프 재정박 vs dt 클램프), 젓기(시뮬 효과 0 코스메틱 vs "소량 활력+쿨다운" 액션)까지 전부 두 벌이다. 원샷 구현자는 어느 쪽을 따를지 추측하게 된다.

**더 단순한 대안**: 닫힌 함수 모델(시뮬 문서)로 단일화. v1 규칙은 전부 경과시간의 함수라 적분기가 필요 없다. 이에 따라 자동 삭제되는 것: `remainderMs`, 고정 스텝 루프, `additivity.test.ts`·`clock.test.ts`의 remainder 검증(닫힌 함수는 가산성이 자명), MAX_CATCHUP 90일(60일 채택). 시계 역행은 시뮬 문서의 재정박 규칙 채택(파생 모델에선 필수, ~5줄). 젓기는 코스메틱(확정 결정 1의 정신과 정합). 상태 저장 vs 파생의 명명·필드도 시뮬 문서 기준으로 통일.

**잃는 것**: 상태끼리 실시간 상호작용하는 미분방정식형 규칙(예: activity가 sourness 증가율에 피드백)을 미래에 넣을 자유. v1 스펙에는 그런 규칙이 하나도 없으므로 실손실 0.

## 2. sim 안의 시드 PRNG — 통째로 삭제

**무엇이 과한가**: `rng.ts`(mulberry32) + state 내 `rngSeed` + 스텝마다 시드 전진 + `Math.random` ESLint 금지 규칙. 그런데 시뮬 스펙 어디에도 확률 이벤트가 없다 — 상태 전이·산미·성숙 전부 결정론적이고, 기포 배치는 렌더 화장품이다.

**더 단순한 대안**: sim에서 랜덤을 전면 제거. 기포·연출의 랜덤은 render 층에서 `Math.random` 그냥 쓴다. ESLint 규칙도 삭제.

**잃는 것**: 기포 배치의 리플레이 결정론 — 아무도 요구하지 않는 성질이다.

## 3. "M0 픽셀 동급 이식" 직후 씬 전면 재구축 — 낭비 구조 + 연출 컷 4건

**무엇이 과한가**: 아키텍처 M0는 "현 프로토타입과 픽셀 동급 무손실 이식"(탑다운 카메라·구도 공식 계승)을 게이트로 삼는데, 비주얼 문서는 카메라를 55° 틸트로 교체하고 유리병 3패스·눈금·고무줄로 씬을 전면 재구축한다. 이식에 들인 정밀도가 바로 버려진다. 여기에 v1 대비 가치가 낮은 연출이 얹혀 있다: **천 덮개**(휴면에만 등장하는 전용 LatheGeometry+주름 셰이딩+트윈 — 휴면 신호는 이미 uCrust·색 바램·숨 정지·hooch 4개), **시간대 틴트**(±4%, 거의 비가시), **물 붓기 리본 메시**(스크롤 셰이더+링 리플, 2.8초 연출 중 0.7초), **어댑티브 성능 가드**(fps 샘플링→DPR 강하 + 유휴 30fps 스로틀 — 드로콜 10 이하·20k tri 씬에 디버깅 세금만 추가).

**더 단순한 대안**: M0부터 새 구도(틸트+병 원통+고무줄)로 커밋하고 "이식"은 셰이더·팔레트·입력 모델로 한정. 틸트·병·고무줄은 유지한다 — 성장 가시화는 게임 성립 조건이다. 컷: 천 덮개, 시간대 틴트, 물 리본(물은 uSpecStr 상승+사운드로 대체), 어댑티브 가드(고정 DPR 상한 2 + hidden 시 rAF 정지만 유지).

**잃는 것**: 휴면 연출 한 겹, 미세한 분위기 두 가지, 극저사양 폰 보험. v2 후보로 밀 수 있다.

## 4. WebAudio 합성 사운드 8종 — 2종으로

**무엇이 과한가**: 필터 체인·8Hz LFO·브라운 노이즈·원형 스테레오 패닝까지 포함한 8종 전량 합성. 오디오 합성 파라미터 튜닝은 셰이더 튜닝만큼 시간을 먹는데, 이 게임은 무음이어도 완전히 성립한다.

**더 단순한 대안**: v1은 2종만 — 밥주기 완료 2음, 해금 3음(triangle 몇 줄이면 됨) + 음소거 토글. 기포 뽀글·사락·물소리·젓기는 후속.

**잃는 것**: 조작 순간의 앰비언스. 보상 사운드 2종이 정서의 8할을 담당하므로 손실은 제한적.

## 5. 기포 시스템도 두 벌 — 프래그먼트 전용 채택

**무엇이 과한가**: 아키텍처 문서는 "프래그먼트에서 시드 기반 이동 범프, 지오메트리 추가 0"으로 확정해 놓고, 비주얼 문서는 CPU 수명주기 관리(스폰 간격·개당 2~4s 생명주기·80ms 음수 터짐) + `uBumpPos[8]/uBumpAmp[8]`을 버텍스·프래그먼트 **양쪽에 다른 첨도로 동기 주입**하는 시스템을 설계했다. 이중 리스트 동기는 문서 스스로 "어긋나면 라이팅이 지오메트리에서 유리된다"고 경고하는 함정이다.

**더 단순한 대안**: 아키텍처 문서 버전 채택 — 프래그먼트 전용 하이라이트 기포(떠올라 커지다 사라짐), CPU 수명주기·버텍스 변위·터짐 잔상 없음.

**잃는 것**: 기하학적 융기감과 "뽁" 터지는 손맛. 활성도에 따른 밀도 변화는 프래그먼트만으로 충분히 전달된다.

## 6. discard 그램 경제 — 두 번째 화폐를 없애라

**무엇이 과한가**: `discard` 0~300g 통이 mass와 별도의 자원 원장이다: 급여마다 `mass−60g` 적립, 레시피별 80~150g 차감, 상한 관리, 통 UI. 판정도 없는 레시피 3종을 위해 화폐 시스템 하나를 통째로 운영한다.

**더 단순한 대안**: 그램 원장 삭제. discard 레시피는 단계 게이트 + "마지막 급여 이후 1회" 쿨다운(lastFedAt 비교 — 새 상태 변수 0개)으로. 덜어내기 자체는 밥주기 **연출 단계로 그대로 남는다** — 없애는 건 그램 회계뿐이다.

**잃는 것**: 그램 리얼리즘과 "모아서 쓰는" 재미 일부. 실물 관례(덜어내기)는 연출로 보존된다.

## 7. 알림 6종 + 조용시간 설정 — 2종 + 고정 클램프로

**무엇이 과한가**: 배고픔·무응답+24h·시큼·휴면·냉장 주간·피크 opt-in 6종에 조건 분기(무응답 시에만, 대체 관계, 사용자 토글)와 조용시간 설정 UI까지. inexact 알람 위에 세운 정밀 스케줄링이다.

**더 단순한 대안**: 2종 — "밥 시간이에요"(냉장이면 주 1회 시각으로 자동 이동, 같은 슬롯) + 휴면 진입 1건 후 침묵. 조용시간은 22~08 고정 상수(설정 항목 아님). 피크 알림·무응답 단계별 문구는 후속.

**잃는 것**: 방치 서사의 세밀한 단계 안내와 굽기 타이밍 편의. 핵심 계약(밥 리마인더 + 스팸 금지)은 그대로 지켜진다.

## 8. 탭 4개·화면 6개 — 탭 2개·화면 4개로 (시뮬 문서가 이미 정답)

**무엇이 과한가**: 아키텍처 문서는 르방/레시피/컬렉션/설정 4탭 + 굽기 스택 화면. 그런데 시뮬 문서 §5-3은 이미 레시피 탭 자체를 도감(실루엣+등급+횟수)으로 설계했다 — 컬렉션이 별도 탭일 이유가 없다. 설정은 알림 토글·음소거·초기화 세 줄짜리다.

**더 단순한 대안**: 탭 2개(르방/레시피) — 프로토타입 구조 그대로. 레시피 카드에 최고 등급·횟수 병기(=도감), 굽기는 카드에서 진입, 설정은 홈 구석 아이콘 → 중앙 모달. router 화면 수 6→4.

**잃는 것**: 거의 없음. 컬렉션 그리드의 전시 효과 정도인데 카드 병기로 대체된다.

## 9. 저장 3중 사다리 + 마이그레이션 픽스처 인프라 선구축

**무엇이 과한가**: 주 슬롯 + prev(last-known-good) + Preferences 미러 3계층 사다리, 그리고 v1 출시 전에 버전별 픽스처 JSON 동결 + 전 체인 마이그레이션 테스트.

**더 단순한 대안**: 주 + 미러 2계층. prev 슬롯이 막는 위험은 "쓰다 만 손상"인데 동기 localStorage에서 half-write는 실질적으로 불가능하고, 실제 위험(WebView 스토리지 evict)은 미러가 커버한다. 버그로 "파싱은 되지만 나쁜 상태"가 저장되는 경우는 검증이 파싱+스키마 가드 수준이라 prev로도 못 막는다 — 즉 prev 제거는 "저장 유실 0" 기준과 충돌하지 않는다. 마이그레이션은 `schemaVersion` 필드 + 빈 체인 자리만 두고, 픽스처 테스트는 첫 실제 마이그레이션이 생길 때 그 버전부터.

**잃는 것**: 극단 손상 시나리오 방어 한 겹과 마이그레이션 사전 리허설. 스키마 버전링 자체(확정 결정 6)는 그대로다.

## 10. 저장 상태 잔여 다이어트 — 파생 가능·중복 필드 제거

**무엇이 과한가**: `unlockedRatios` 배열(3단계=1:2:2, 4단계=1:5:5로 **stage에서 완전 파생** — 시뮬 문서 자신의 "파생은 저장하지 않는다" 원칙 위반), 아키텍처 문서의 `feedCount`(maturity와 중복), `name`/`rename` 액션(시뮬 문서에는 없고, 5단계 해금 보상 "병 이름표"와 온보딩 이름 짓기가 서로 충돌 — 어느 쪽인지 미통일), settings의 `quietStart/quietEnd`(발견 7 채택 시 상수).

**더 단순한 대안**: `unlockedRatios`·`feedCount`·quiet 시각 삭제. 이름은 하나로 통일 — 온보딩은 이름 없이 시작하고 5단계 보상으로 이름표를 여는 시뮬 문서 쪽이 콘텐츠도 겸하므로 그쪽 채택. 저장 필드는 "삭제하면 복원 불가능한 것"만 남긴다.

**잃는 것**: 없음. 오히려 마이그레이션 표면과 검증 가드가 줄어든다.
